# Mapping to the Case Study 2 evaluation criteria

This maps each criterion to concrete evidence, with **genuine strengths** and **remaining gaps**.
I've deliberately not assigned a self-score; judges score, and the evidence is listed so they can check it.

| Criterion (weight) | What the judges assess | Genuine strengths (evidence) | Remaining gaps |
|---|---|---|---|
| **Problem understanding (15 %)** | Clear application, scope, requirements, explanation of the battery challenge | Scope fixed to a low-voltage 4S LFP solar-storage module; team requirements REQ-01..03 stated as team-proposed; every case-study challenge (cross-discipline data, trade-offs, variation, limited data, scope) maps to a module (`../BatteryX_Plan/BATTERYX_AI_PRD.md` §1) | Requirements are team-proposed, not from a real customer; the application is generic |
| **Desirability (15 %)** | Value to users, relevance | Students and early-stage engineers get cross-discipline impact in one place; flags show exactly which datasheet value blocks which check; report produced in one click; free and open stack | No user testing or interviews yet, so desirability is argued, not measured |
| **Technical feasibility (20 %)** | Simple, safe, achievable with available time, data and resources | Runs on a student laptop: full evaluation of one design 0.04 s median, A/B/C comparison 0.11 s, whole browser workflow 68 s (measured 2026-11-09); open-source stack; SQLite fallback when Atlas is offline; AI optional; low-voltage scope; 146 automated tests | Atlas and AI require internet; no authentication for multi-user use |
| **Engineering quality (15 %)** | Sound calculations, assumptions, system interactions | Stated equations with dimension checks and analytical tests (RC step, CC→CV transition, energy conservation); coupled electro-thermal; protection coordination (fuse vs BMS vs cell); every input source-tagged; assumptions and unsupported calculations flagged (`AUDIT_REPORT.md` §3) | First-order models only; single-node thermal (no cell-to-cell spread); illustrative cell data; **no validation against measurements** |
| **Prototype & evidence (15 %)** | Working demonstration with measurable, repeatable results | Working full-stack app; real-browser workflow 14/14 with screenshots; 10 reproducible scenarios regenerated by script (`DEMO_RESULTS.md`); parity with the stage-1 engine | Evidence is model output and software verification, not test-bench data; Claude copilot not yet run live |
| **Innovation (10 %)** | Creative but understandable improvement over the starting design | Cross-subsystem change propagation; constraint-first comparison with stated trade-offs; **AI copilot that cannot fabricate**: tool-only numbers, whitelisted design changes, backend verifier with repair loop, ten incorrect-claim tests | The innovation is in the workflow and AI guardrails, not in new battery physics |
| **Business viability (10 %)** | Value in cost, performance, safety, usability, scalability | Reusable cell and component libraries, report automation, education and startup use cases, low running cost (open source, optional AI) | No pricing, market sizing or customer validation; benefits are hypotheses |

## Where the stage-1 starting design improved (for the "Innovation" story)

| Stage 1 (prototype) | Stage 2 (this platform) |
|---|---|
| Browser-only JS model, 19 closed-form calcs | Python engine with a time-domain ECM, CC-CV, coupled thermal, 15 rule checks, 11 versioned models |
| Template "copilot" text | Claude tool-calling copilot with backend verification |
| No persistence | Projects, cells and conversations in MongoDB Atlas |
| Change log only | Input → model → result → check traceability in every report |
| Example values | Same values, now **labelled illustrative everywhere**, plus a datasheet entry path that refuses invented data |
